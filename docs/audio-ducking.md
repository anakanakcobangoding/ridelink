# Audio ducking

RideLink ducks only the local shared music element. It never changes the remote WebRTC audio element, microphone track, server playback position, room state, or another rider's volume. The music element is routed through `MediaElementAudioSourceNode → user GainNode → navigation GainNode → output analyser → destination`. The analyser sits after the gains and is used only to verify the rendered music level in browser tests.

The default music gain follows the rider's local volume setting. When Web Speech reports an instruction `start`, the navigation gain ramps to `0.25` in 250 ms. A completed instruction holds that level for 150 ms and ramps back to `1` in 700 ms. Speech error or cancellation starts restoration immediately. Instruction IDs ensure stale completion events cannot restore music underneath a newer instruction. Stopping navigation resets the local gain. Rapid instructions replace the current automation from its current estimated gain.

AudioContext creation, resume, and media playback are initiated from music controls, which are user gestures. If graph construction or playback is unavailable, RideLink falls back to a short animation-frame fade using the music element's volume property. The fallback is best effort; browser and device volume behavior differs. The player displays the ducking state alongside the existing polite music status.

On iOS Safari, playback and Web Audio graph activation require user interaction, and behavior may differ when Safari enters the background, the screen locks, or Bluetooth switches into call audio mode. The HTML media volume property is not a reliable way to control system volume on iOS. RideLink does not change iPhone system volume or other apps' audio. Physical iPhone/Safari/Bluetooth tests have not been performed for this stage, so ducking quality on those devices is unverified. Keep Safari foreground and the device unlocked during an initial test, and do not operate the phone while riding.

Automated coverage uses fake clocks and GainNode-compatible test doubles for fade scheduling, cancellation, stale events, overlapping instructions, per-rider isolation, fallback, and cleanup. The Playwright test uses two independent browser contexts, actual local music audio, a real Web Audio graph and analyser, while replacing speech synthesis with a deterministic browser test double. It checks that the measured music output falls for the speaking rider and stays at normal level for the other rider. This verifies browser audio graph attenuation; it does not verify audible speech output, Bluetooth behavior, iPhone Safari, or background playback.
